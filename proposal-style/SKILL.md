# Proposal style

A proposal is judged by reviewers, many of them outside the immediate subfield, who have little time per proposal. This skill helps such a reviewer find, quickly and without decoding, the research question, the evidence that it is open, the planned work and the outcome that can be assessed. You need the call's template and criteria, the scientific case with its numbers, and the facts only the applicant can give. You get the drafted or revised text, with the evidence gaps listed separately. For experimental manuscripts, use `clear-experimental-writing` instead of imposing a grant structure.

## Where this fits

- Comes from: the quantitative case built with `proposal-analysis` and the numbers file and registers of a `proposal-project` directory.
- Goes to: the proposal text in that directory; the interview talk, if there is one, is built with `research-slides`.
- Checked by: the style editor and the specialist referee of the simulated review cycle in `proposal-analysis`, and `citation-checker` for the references.

## Guidance

Read [style-guide.md](references/style-guide.md) for the section patterns, objective and work-package structure, risk treatment and revision checklist. Use only the parts relevant to the requested section; an abstract or a short edit does not need the whole proposal template.

Scientific accuracy comes before persuasive effect. Never invent citations, prior attempts, collaborator commitments, feasibility numbers or personal credentials. Keep uncertainties and caveats that change the interpretation. State established results plainly, present untested ideas as hypotheses, and use firm future language only for work the team controls; name external dependencies.

Prefer plain research questions, evidence followed by what it implies, parallel work packages and sparing emphasis reserved for objectives and commitments. Any numerical guidance in the style guide is a rule of thumb, not a quota. The funder's template, page limits and evaluation criteria override this guide, as does the user's own format.

Use `proposal-project` for the proposal directory and registers and `proposal-analysis` for the quantitative case.

## What to deliver

For revisions, keep the technical meaning and make only the level of change requested. Return the revised text and list substantive evidence gaps separately rather than filling them silently. Check that each question, objective, method, risk and deliverable can be traced to the others.
