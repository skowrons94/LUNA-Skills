# Proposal project layout

```
ACRONYM/
├── README.md                 what the proposal is, where the current PDFs are, how to rebuild
├── proposal/
│   ├── source/               current text of each part (summary, scientific case, CV, budget, abstract)
│   ├── numbers.tex           macros for every quoted number (generated or checked by a script)
│   ├── references.bib
│   ├── figures/              figure files used by the text (generated by analysis/scripts)
│   ├── build/                PDFs, DOCX and logs (rebuilt, never edited)
│   ├── review/               simulated or real reviews, one file per reviewer and round, plus change logs
│   └── archive/vN/           superseded sources and builds, unchanged
├── analysis/
│   ├── README.md             what each script computes and which result files feed which sentence
│   ├── scripts/              thin, re-runnable scripts (feasibility, design, power, back-tests, figures)
│   ├── results/              numerical outputs (JSON/CSV) with the script and inputs that made them
│   ├── plots/                diagnostic and proposal figures
│   └── data/                 only small inputs specific to the proposal; link the feasibility project for everything else
├── docs/
│   ├── CALL.md               call rules: edition, page limits, budget caps, criteria, deadline
│   ├── DECISIONS.md          dated decisions on framing, scope and numbers, with reasons
│   ├── OBJECTIONS.md         reviewer objections: status, answer, evidence path
│   ├── INPUTS_PI.md          facts only the PI can give, as received (dated)
│   └── FINAL_CHECKLIST.md    open placeholders, letters, quotes, pre-submission checks
└── private/                  git-ignored: other people's proposals, internal reports, confidential notes
```

## Versioning

- Keep one current version of each part in `proposal/source/`. Before a substantial revision, copy the current source and its build to `proposal/archive/vN/` and record the change in `proposal/review/vN_changes.md`.
- Name builds by part and version (`ACRONYM_case_v12.pdf`) so a reviewer comment can be traced to the text it refers to.
- Never edit files in `build/` or `archive/`. Empty scaffold directories carry a `.gitkeep` so that they survive a clone.

## Number provenance

- Every number in the text appears once in `numbers.tex` (or the equivalent for DOCX builds) with a comment naming the result file and key.
- When a result changes, regenerate the macros and rebuild all parts; grep the sources for hard-typed copies.
- Rounding is a text decision: keep full precision in `results/`, round in the macro, and use the same rounding in every part and figure.

## Placeholders

- `[[PI: …]]` marks a fact only the applicant can supply (letters, quotes, CV items, roles, availability, personal circumstances). `\todo{…}` or a red macro is acceptable in LaTeX.
- A placeholder is never a guess. If a number is estimated, write it as an estimate with its basis.
- Before submission, every placeholder is either resolved or deliberately removed together with the claim that depended on it.

## Combining with other skills

- `nuclear-research-project` for the reproducible analysis or feasibility study behind the proposal (data, R-matrix, simulation, report).
- `proposal-analysis` for feasibility, design, decision rules, back-tests and the simulated-review cycle; `target-analysis` and `efficiency-analysis` for stopping powers, target profiles and detection efficiencies behind the rate estimates.
- `proposal-style` for the prose; `prc-figures` for figures; `research-slides` for the interview talk.
