# Layout of a measurement project

The same tree is used for every campaign, so that a reader who knows one project finds everything in another, and so that
two analyses of the same reaction (for example a 2002 HPGe campaign and a 2025 BGO campaign) can be compared stage by
stage. Folders that a project does not need are left out; the meaning of a folder that exists never changes.

```text
<reaction>_<setup>_<target>_<years>/        e.g. 14npg_bgo_solid_2023-2025, 19fpag_bgo_implanted_2024-2026
|-- README.md          campaign: reaction, facility, setup, targets, people, publications, data sources, what was not copied
|-- CLAUDE.md          the case for an agent: question, conventions, where things are, traps found so far
|-- HANDOFF.md         goal, status, open problems, next steps; updated at the end of every session
|-- PROBLEMS.md        problematic runs, inputs and effects, with evidence and status (template in assets/)
|-- LITERATURE.md      every reference used: citation, DOI, local file, what it is used for, verified (yes/no)
|-- DECISIONS.md       decisions with options, who decided, date and consequences
|-- ASSUMPTIONS.md     assumptions in force, with their size and how they are tested
|-- CHANGELOG.md       dated entries: results that changed, promotions from _claude/, reruns
|-- data/
|   |-- raw/YYYY-MM[_campaign]/   original files exactly as received (read-only), one folder per month or campaign
|   |-- root/YYYY-MM/<run>.root   one ROOT file per run (TTree + TH1 per channel + metadata), generated by tools/
|   |-- external/                 exfor/, literature/ (digitised or transcribed tables), collaborators/<name>/
|   |-- logbook.csv               one row per run, generated by tools/build_logbook.py (data-and-logbook.md)
|   |-- logbook_sources/          the original logbooks (xlsx, ods, txt) as received, read-only
|   |-- file_map.csv              source_path, local_path, sha256, note for every file in raw/ and logbook_sources/
|   `-- MANIFEST.sha256           checksums of raw/ and root/, regenerated after every conversion
|-- docs/
|   |-- papers/  theses/  manuals/  talks/  drawings/  photos/
|   |-- elog/                     ELOG exports (text and PDF), one folder per logbook
|   |-- shift_reports/            shift reports and meeting minutes
|   `-- correspondence/<person>/  e-mails and notes, one folder per person
|-- analysis/
|   |-- 00_audit/          run classification, charge and time checks, duplicates, excluded runs
|   |-- 01_beam/           accelerator energy calibration, energy spread, charge integration, dead time
|   |-- 02_calibration/    detector energy calibration and resolution per channel and period
|   |-- 03_background/     room/ (environmental, cosmic, intrinsic) and contaminants/ (beam-induced lines)
|   |-- 04_efficiency/     full-energy and total efficiency, summing, angular correlations, distance and spot effects
|   |-- 05_target/         profiles from resonance scans, stoichiometry, stopping powers, degradation in time
|   |-- 06_yield/          peak areas and yields per run and per point, normalised to charge and live time
|   |-- 07_sfactor/        cross sections and S factors, effective energies, uncertainty budget, comparison
|   |-- 08_rmatrix/        AZURE2 fits and extrapolations using 07 (and external data with provenance)
|   `-- 09_rate/           reaction rate and astrophysical impact (networks, stellar models)
|-- simulation/            geometry/, macros/, runs/<name>/ (manifest per run), validation/; used by 03, 04, 05
|-- tools/                 readers, converters and their validation, build_logbook.py, make_report_tables.py, style
|-- report/                main.tex, sections/, tables/ (generated), figures/ (links or copies made by scripts),
|   `-- build/             LaTeX output (main.pdf); not edited by hand
|-- slides/YYYY-MM-DD_<event>/   one folder per talk: build script, figures, the .pptx or .pdf
`-- _claude/YYYY-MM-DD_<topic>/   exploratory work (ignored by git), promoted only when validated
```

## Inside a stage

Every `analysis/NN_<stage>/` has the same parts: the scripts at the top level, numbered when their order matters;
`inputs/` for external tables the stage needs, each with its provenance line; `results/` for everything later stages
read; `figures/` for plots; and `README.md`, the stage report. The README states the question of the stage, its inputs
(files and versions), the method in a few paragraphs, the checks with their outcome, the gate result and who judged it,
and the command that regenerates every result. Variants of a fit go in `results/<variant>/` with one naming pattern
across the project, so that a systematic uncertainty can be computed by looping over folder names.

## Names

Folders and files are lowercase, `a-z0-9` with `_` between words and `-` only inside dates and ranges; the uppercase
exceptions are README.md, HANDOFF.md, CLAUDE.md, PROBLEMS.md, LITERATURE.md, DECISIONS.md, ASSUMPTIONS.md, CHANGELOG.md
and MANIFEST.sha256. Original data files keep their original name, lowercased, with spaces and special characters
replaced by `_`, because spreadsheets, logbooks and the server refer to them by that name; `file_map.csv` keeps the
original path. Dates come first when they order things (`2025-02_scans`). Never in the tree: `*.bak`, `*copy*`,
`tmp*`, `_out_*`, dated duplicates of a file, or logs of runs that were only checks.

## What goes where when in doubt

A file that came from outside the analysis goes to `data/` (measurements and comparison data) or `docs/` (documents);
a file the analysis made goes to the stage that made it. A number used in two stages lives in the results of the
first and is read from there. A simulation that serves one stage only may live in that stage; one used by several
(an efficiency model also used for summing and background shapes) lives in `simulation/`. Code used by more than one
stage goes to `tools/`. Superseded material is archived with a manifest, not deleted.

## Version control

The project is a git repository. `data/raw/`, `data/root/` and `simulation/runs/` are excluded from git because of
their size; their integrity is guaranteed by `MANIFEST.sha256`, which is committed. Results small enough to diff
(csv, json, tex tables) are committed, so that a change in a number shows up in the history.
